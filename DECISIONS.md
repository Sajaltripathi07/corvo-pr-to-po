# DECISIONS.md: assumptions and how ambiguity was handled

Each item: what was unclear, what the app does, and where to change it (almost always the policy document, not code).

## Policy interpretation
1. **Requirement date** = date of the first (earliest-created) line in a clubbed requirement. Contract validity, "bought in last 365 days", preferred-list windows and the policy version in force are all evaluated as of that date.
2. **Clubbing** (policy 2): "within 14 calendar days" compares *calendar dates* of `created_at` (time ignored) against the requirement's **first** line; need-by must be within 7 days of the first line's need-by. A line joins the **earliest** open requirement it qualifies for. New items are never clubbed. Missing need-by dates do not block clubbing. Windows live in `clubbing.*` of the policy.
3. **Order of processing**: lines are sorted by `created_at`, then PR number, then line number, *not* by file order or PR number. (The sample batch contains PR-174/175 created before PR-1.)
4. **Contract ceilings** are consumed in requirement-date order, only by requirements that actually go to a contract PO. Fit test is `consumed + this requirement's value at that contract's rate <= ceiling` (equal is allowed). If several contracts fit, the **lowest rate** wins (tie: contract id). Contracts held by a non-Active supplier (e.g. S004 Blocked) are ignored entirely. Each batch run starts from the register's consumed values (runs are independent simulations, so run 1 and run 2 are comparable).
5. **PDF-only contracts** are added through the Contracts page (read from the PDF, reviewed by a person). Ceiling consumption starts at 0, and they apply from their own start date (inclusive). The register is not trusted to be complete, and where PDF and register disagree the app uses what is stored; nothing is merged silently.
6. **Valuation** (3.1): contract rate -> lowest applicable contract rate if every applicable contract is out of ceiling -> price of the most recent PO in the 365 days *before* the requirement date -> item-master standard price. The requester's estimate is used **only** for new items. POs issued by the app are not fed back into history during a run.
7. **Emergency**: a requirement is Emergency if *any* clubbed line is marked `Emergency` in the `urgency` field. A description that says "urgent" with urgency=Normal is **not** treated as Emergency (the field is authoritative) but is flagged for the buyer.
8. **Rule 5.3/5.4 supplier**: "preferred supplier #1" at its reference price (latest PO price from that supplier in the window, else its latest contract rate). Limits are exactly as written: emergency `<= 5,00,000`, spot `< 2,00,000`, RFQ `< 10,00,000`.
9. **Item code vs description**: a valid item code wins. An unknown code falls back to matching the description (flagged). A description is matched by a deterministic token matcher with abbreviation/noise lists stored in the policy; anything below the confidence bar becomes a **new item** and is never forced onto a "close" master item. A different size or spec ("M12" vs "M10") is a different item.
10. **Preferred list** (policy 6): history window 548 days (strictly before the date); contract holders count even if the contract has expired but must have started on/before the date; Blocked/Inactive excluded. Score = 0.30 frequency (PO count / busiest supplier's count) + 0.25 recency (1.0 <=90 days, 0.5 <=365, else 0) + 0.15 held a contract + 0.15 on-time + 0.15 quality/5, reconstructed from the worked examples (which it reproduces). Ties: on-time, quality, supplier id. Weights/tiers live in `preferred_list.*`.
11. **Top-up suggestions** rank other Active suppliers listing the item's category by `0.5 x on-time + 0.5 x quality/5` (the worked examples, including the electrical-spares RFP with only four eligible suppliers, require a blend rather than on-time alone). Fewer suppliers than requested are returned rather than padded.
12. **PO consolidation** (7.1): same supplier + plant + route, requirement's first-line creation time within 24 hours of the PO's first requirement; earliest qualifying PO wins. PO numbers (`PO-0001`...) follow creation order of the PO's first requirement. Note that the worked-examples numbering is one lower than ours from PO-0002 on, because the batch has two servo-drive lines created at 08:10 on 2 Nov that become the first PO; grouping, not numbering, is what is meaningful.

## Data quality
13. Lines that cannot be decided get route `NOT_PROCESSED`, an empty decision and the reason: quantity <= 0, unknown plant (PUN2), unreadable `created_at`, no item code and no description, duplicate PR number/line (first occurrence is processed).
14. New items without an estimated price are valued at 0 and flagged.
15. `group_value_inr` is written to 2 decimals (the worked examples round to whole rupees).

## Policy as data
16. **Which version applies**: the version whose `effective_from` is the latest on or before each requirement's date. Run 1 can be forced to a specific version (`policy_version=5.0` on the API / dropdown in the UI); default is by date. Approving an amendment with a *future* effective date therefore changes nothing for earlier requirements, by design. For the blind test, the amendment's own effective date decides; if it is later than the batch, use "Latest approved policy" in the UI (`policy_mode=latest`).
17. **A policy edit never activates by itself.** Upload -> draft -> plain-language diff + impact on the last batch -> human approval. Approval is limited to the "Procurement head" role. A draft that fails validation (unknown fact, PO without a supplier mode, duplicate rule id) cannot be approved.
18. **Rule language**: conditions over a fixed fact catalogue (value, plant, category, item type, emergency, contract usable, bought-recently, ...) with `all/any/not`; outcomes name a decision, route and supplier mode. New *kinds* of rule (plant-specific limits, category rules, reordering) are therefore data. What needs code: a brand-new fact (e.g. a supplier-diversity score) or a new supplier-selection mode.
19. If a rule's conditions match but no eligible Active supplier exists for its outcome (e.g. no preferred supplier), the rule is skipped and the next one is tried (shown in the trace). If nothing matches, the requirement defaults to RFP and is flagged.

## Product scope
20. **Identity** is a name + role chosen in the header (requester / buyer / procurement head) and enforced server-side by role; there is no login. A real deployment would put SSO in front of this.
21. **Chat PRs** go into a "live pool" that is re-decided as new requests arrive (so splitting across requests is still caught). Once a buyer approves/overrides a requirement it is frozen: later requests cannot join it, and its contract consumption counts against ceilings.
22. Overrides require a written reason, cannot name a Blocked/Inactive supplier, and keep the original decision in the audit trail. Documents (PO/RFQ/RFP numbers) are per run.
